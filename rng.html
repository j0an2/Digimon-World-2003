Random numbers

How the original European version (SLES-03936) makes its random numbers, read from its decompiled code (dw3_decomp, src/main/system/random.c): what decides whether a hit lands, which battle starts and what an enemy drops, and how much of it can be controlled.

A table, not a formula

The game doesn't compute random numbers. It has a fixed table of 4096 numbers, RANDOM_TABLE, and reads it in order: each call returns the next entry, and after the last one it starts again from the first.

random():  index = (index + 1) & 4095
           return RANDOM_TABLE[index]          (0 to 4095)
  • It starts at entry 0 when the console is switched on (RANDOM.seed(0) in main.c), every time.
  • It moves on one entry every frame, whatever is happening: the main loop calls RANDOM.next() once per frame and throws the number away. At 50 frames a second (PAL) the table goes round about every 82 seconds.
  • It also moves on every time something asks for a number: a hit roll, a critical roll, the battle camera's next shot, a face blinking in battle, the step counter to the next battle…
  • Its position isn't saved: it isn't part of the memory card's save, so after loading a save it is wherever the time since power-on (and everything since) left it. A savestate of an emulator does keep it.
  • The table holds every number from 0 to 4095 exactly once. So over one turn of the table every outcome comes up exactly as often as it should: each value of a hit roll (0–127) 32 times, each battle slot (0–7) 512 times.

Every roll takes the next entry and keeps part of it:

So a hit with a chance of 110/128 lands when the entry's last 7 bits are 0–109, and misses when they are 110–127. See the battle formulas for how each chance is worked out.

Can it be manipulated?

Everything is deterministic: from the same position, the same inputs on the same frames give exactly the same results. What decides a roll is the frame the action happens on, since every frame moves the table on by one.

  • With savestates (an emulator, or the native port's quick save): yes, completely. Load a state from just before an attack and the result is always the same. To change it, wait a few frames before confirming: the roll reads a different entry. That is also why retrying a drop from the same savestate gives the same item every time.
  • Tool-assisted (TAS): yes. A tool can press each button on the exact frame that gives the wanted result.
  • By hand, in real time: practically no. The difference between a hit and a miss can be one frame, 1/50 of a second, and animations, camera shots and blinking faces take numbers too, so the count between pressing a button and the roll isn't something a player can follow.
  • The step counter is the exception. GAME.battleSteps is saved with the game and only goes down while walking in an area with battles: the steps to the next battle are fixed once rolled, and reloading a save gives the same ones. Which battle it is, though, depends on the frame of the last step.

What a real-time run can do is make the rolls matter less: more Speed and level than the enemy, and techniques with high accuracy (127 and over never miss once the user is a little above the target).
